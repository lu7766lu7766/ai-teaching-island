安全使用 AI 的七條守則

① 個資與機密不貼：身分證字號、病歷、成績、公司內部文件、帳號密碼都不要貼進免費 AI 服務；免費方案的對話可能被用來改善服務。 ② 重要資訊要查證：數字、日期、法規、醫療與財務相關內容，一律以原始來源為準。 ③ 尊重著作權：不要把別人的作品整份貼上、改寫後當成自己的；不要用真人照片做出對方沒做過的事；AI 產出的圖文要公開發表或商用前，先確認平台條款與引用規範，並標示 AI 生成（第 3 站）。 ④ 誠實揭露：作業、報告或工作文件用到 AI 時，依學校或公司規定說明哪些部分有 AI 協助；最後的判斷與責任在你。 ⑤ 管好金鑰與權限：API Key 不放前端、不上網（第 9、10 站）；給 AI 工具的權限越小越好，讓 Agent 改檔案或執行指令前，先設好權限、看過再同意（第 11 站）。 ⑥ 小心提示注入：網頁、郵件、檔案裡的文字可能夾帶命令，騙 AI 照做；AI 讀進來的內容是資料，不是你的指令（第 12 站）。 ⑦ 後果大的事由人決定：刪除資料、付款、對外發送，以及評分、篩選人選這類判斷，由人做最後一步。模型會複製訓練資料裡的偏見，用在評價人的場合更要親自看過。

AI 工具的六種形態：挑對傢伙

產品名稱常換，但形態很少變。先看任務適合哪一種，再挑工具： 網頁版：打開瀏覽器就能用，適合隨手問、寫字、找資料；碰不到你電腦裡的檔案。例如 Gemini、Gemini Notebook、ChatGPT（第 2、3 站）。 手機 App：適合拍照問、語音輸入；打長字、讀長文不方便。例如 Gemini App。 桌面版：裝在電腦上，能讀本機資料夾。例如 OpenCode 桌面版（第 7 站）。 編輯器內：住在寫程式的軟體裡，適合改程式、看整個專案。例如在 VS Code 裝 AI 外掛。 命令列代理：在終端機裡真的動手改檔、執行指令，能力最強、權限也最大，最需要設好規則與權限。例如 OpenCode 終端機版（第 7、11 站）。 API 串接：讓你的程式去呼叫 AI，適合重複執行、做成產品；需要一點程式能力與金鑰（第 9、10 站）。

1. 水晶球觀測所

L1 基礎｜認識 AI 怎麼運作：文字接龍、Token 與上下文、幻覺

學習目標：能用自己的話說明 AI 如何產生回答、Token 與上下文是什麼、為什麼會說錯，並知道哪些事適合交給 AI、哪些要自己把關。

AI 怎麼回答你：一台超會接龍的文字預測機

Gemini 這類聊天 AI 的核心是「大型語言模型」（LLM, Large Language Model）。它從大量文字中學到字詞之間的規律，回答時是根據你的問題，一小段一小段地預測「接下來最可能出現的文字」，再接成完整的句子。 所以它特別擅長跟語言有關的工作：寫作、改寫、摘要、翻譯、整理、發想。但它不是資料庫，也不是計算機；它產生的是「看起來最合理的文字」，不保證每句都是事實。 同一個問題問兩次，答案可能不一樣，這是正常的：預測帶有一點隨機性。不滿意就重新產生，或多問幾次挑最好的版本。

Token 與上下文：AI 的短期記憶

AI 不是一個字一個字讀，而是把文字切成叫做 Token 的小片段，怎麼切依模型而定。使用額度、API 計費和回答長度上限，都是用 Token 計算。 AI 每次回答時能同時看到的內容有上限，叫做「上下文長度」（context window），包含你這次的問題、前面的對話、上傳的檔案，以及它自己說過的話。對話拉得很長時，前面交代的規則可能被淡忘，或超出它看得到的範圍。 另外要分清楚：上下文是「這一次看得到多少」，記憶是「下一次還記不記得」。模型本身不會記得你，產品裡的「記憶」功能或 AGENTS.md，其實都是把資料存在外面，下次再自動放回上下文。 小技巧：換新主題就開新對話；重要的要求放在開頭或結尾，不要埋在一大段資料中間；長對話中把重要規則再提醒一次；需要每次都遵守的規則，寫成 System Prompt（第 6 站）或 AGENTS.md（第 8 站）。

為什麼 AI 會說錯：幻覺與知識截止

因為 AI 是在「產生合理的文字」而不是查證事實，它可能編出不存在的書名、網址、數據或引用，而且語氣非常肯定，這叫做「幻覺」（hallucination）。 模型的知識來自訓練資料，訓練之後才發生的事它不一定知道，這叫做「知識截止」。有時 Gemini 會上網搜尋來補充，但搜尋到的資料也可能過時或有錯。 降低幻覺的方法：先提供資料，請它「只根據這份資料回答」；請它標出不確定的地方，不知道就說不知道；要求附上來源，再自己點開確認。

工作類型交給 AI 的程度原因
寫作、改寫、摘要、翻譯、發想✅ 很適合，再自己潤飾這是語言模型最擅長的事
整理你提供的資料✅ 適合，記得對照原文答案有資料當根據，比較不會亂編

2. 咒語入門島

L2 入門｜用 Gemini 免費版學會好好提問，用 Gemini Notebook 根據資料提問

學習目標：能用「角色、任務、背景、限制、格式」五要素寫出具體提問，追問與查證 AI 的回答，並用 Gemini Notebook 讓 AI 只根據你的資料回答。

零成本開始：只要一個 Google 帳號

打開 gemini.google.com（或手機 Gemini App），用 Google 帳號登入就能免費使用。免費版可以聊天、上傳圖片或檔案請它說明，也能用 Canvas 一起編寫文件。輸入不只能打字：拍照、截圖、語音、PDF 都能直接丟給它，這叫做「多模態」。 免費版有使用量上限，忙碌時段較強的模型或深入研究等功能可能被限制；額度與模型名稱會依 Google 調整，以畫面顯示為準。 本課程只使用免費功能；遇到需要付費方案的功能（例如 Gemini Spark、Skills、Workspace Studio 自動化），後面的課程改用免費的 OpenCode 完成。

提問五要素：角色、任務、背景、限制、格式

AI 不知道你腦中的情境，資訊給得越具體，結果越貼近需求。 把提問拆成五個要素：角色（用什麼身分回答）、任務（要做什麼）、背景（對象與目的）、限制（字數、語氣、禁止事項）、格式（表格、條列、步驟）。 不必每次五項都寫滿；先寫任務，再補上最影響結果的一兩項，就會明顯進步。 其中「角色」主要影響語氣與用詞，不會讓答案變得更正確；想要正確，靠的是給足背景資料，再加上自己查證。

追問、改寫與查證

和提問一樣，產圖也要把畫面交代清楚。把描述拆成五個要素：主體（畫什麼、在做什麼）、場景（在哪裡、什麼時間）、風格（水彩、Q 版 3D、扁平插畫、寫實照片）、構圖（近景或遠景、角度、橫式或直式）、光線與色彩（光源、氣氛、主色）。 用完整句子描述畫面，比堆一串關鍵字更有效，例如「一隻戴巫師帽的橘色小貓坐在書堆上看書」比「貓、巫師帽、書」清楚得多。 用途也要說：做簡報封面、社群貼文還是學習單插圖？AI 會依用途調整構圖與留白；需要特定比例時，直接寫「橫式 16:9」或「正方形 1:1」。

圖片裡的文字與常見問題

新一代模型已經能在圖片裡寫字，但中文字仍可能出錯或變形。重要的標題、日期、數字，建議產圖後用簡報或修圖工具自己加上去，比較保險。 常見問題：手指或物品細節怪怪的、比例不對、多出不需要的東西。可以直接指出「左手有六根手指，請修正」，或請它重新產生；放大檢查細節再使用。 如果它拒絕產圖，通常是提示詞碰到安全規範，例如真實名人、暴力或侵權內容；換個描述方式或改成原創角色即可。

不要要求 AI 模仿特定在世藝術家的畫風，也不要產出知名卡通角色、品牌商標來公開使用或商用，可能侵犯著作權或商標權。 不要用真人照片做出對方沒做過的事，也不要做假新聞、假證件或冒充他人的圖片，這可能違法，也會傷害別人。 Gemini 產出的圖片會加上看得見的標記和 Google 的隱形浮水印 SynthID，用來辨識是 AI 生成；公開使用 AI 圖片時，最好也主動標示「AI 生成」。 商用前先看平台的使用條款，不同工具與國家的規定不同，而且還在變動。

5. 符文研究所

L5 進階提問｜提示詞工程：範例、拆解、自我檢查與評估

學習目標：AI 做不好時能診斷原因、補上引導；會用範例（Few-shot）、任務拆解與串接、自我檢查，並用固定測試題比較提示詞版本。

AI 做不好時：罵它沒用，給它更完整的引導

AI 回答不理想，最常見的原因是它缺了某些資訊，而不是它「不努力」。大寫、驚嘆號、責罵或威脅都沒有提供新資訊，只會讓下一次回答一樣離題。 請先像醫生一樣診斷：它缺了背景資料？不知道你要的樣子？任務一次塞太多？還是沒有判斷標準？再針對原因補上引導（對照本島上方表格）。 具體回饋的寫法：「你寫的是 A，我需要的是 B，因為 C。請保留 D，只修改 E。」 如果對話已經被錯誤方向帶偏，與其在原對話裡反覆糾正，不如開新對話，把補齊後的完整提示詞一次給清楚。 這座島的四種技巧（範例、拆解、自我檢查、評估），都是「把引導給完整」的具體方法。

給範例：Few-shot 提示

文字很難說清楚「我要的感覺」時，直接給範例最有效。只給任務叫 Zero-shot，附上幾個「輸入→輸出」範例就叫 Few-shot。 訣竅一：給 2～5 個範例，用「範例 1」「輸入：」「輸出：」等標記，和要處理的新資料清楚分開。 訣竅二：範例之間要有變化（長短、主題不同），只給一種範例，AI 會連不該模仿的細節（例如固定字數、同一個開頭）也一起照抄。 訣竅三：範例的格式必須完全一致，AI 會以範例為準，甚至比文字說明更優先；範例裡有錯字，它也可能跟著錯。 訣竅四：範例要示範「應該怎麼做」，不要放「錯誤示範」，AI 可能把錯誤示範也學起來。 訣竅五：範例和文字規則要一致，衝突時先修正範例。

拆解與串接：把大任務切成小步驟

一次要求「讀完資料、整理重點、寫成文章、再做成簡報」，AI 很容易漏東漏西。把大任務拆成小步驟，每一步的產出當成下一步的輸入，這叫提示詞串接（Prompt Chaining）。 好處：每一步都能檢查、修正後再往下走，錯誤不會一路累積；某一步不滿意，只要重做那一步。 常用拆法：① 擷取重點 → ② 擬大綱 → ③ 寫初稿 → ④ 依檢查清單修改 → ⑤ 調整語氣與格式。 需要判斷或分析時，請它「先列出判斷依據或推理步驟，再下結論」。新一代具備思考能力的模型會自行推理，不必刻意寫「一步一步想」，但把依據列出來，可以讓你檢查它的理由是否站得住。注意：它寫出來的推理過程只是它的說法，不是證據，結論一樣要驗證。

自我檢查：讓 AI 先檢查再交件

在提示詞最後加上一份檢查清單，請 AI 交件前逐條核對，例如：是否符合字數？是否回答了每個問題？是否有沒根據的數字？ 也可以分成兩輪：先產出，再請它「以嚴格審稿者的角度找出 3 個最大問題並修正」。把產出和審查分開，通常比一次要求完美更有效。 請它把沒把握的內容標示「待查證」，比讓它硬給答案更安全。 提醒：自我檢查能減少錯誤，但不能保證正確；事實、數字與引用來源仍要由人查證。

評估與迭代：用固定測試題比較提示詞版本

憑感覺說「這版好像比較好」不可靠。準備 3～5 個固定的測試輸入，包含常見情況與一兩個刁鑽的特殊情況，每次修改提示詞都用同一組測試跑一次。 先定好評分標準（例如：正確性、完整度、格式、語氣，各 1～5 分），再比較新舊版本的分數。 一次只改一個地方，才知道是哪個改動造成差異；把每一版提示詞與結果記錄下來（v1、v2、v3），好的版本就能隨時找回來。 免費練習：在 Gemini 或 Google AI Studio 開兩個新對話，分別貼上新舊版本、輸入同一組測試題比較。依 Gemini API 官方條款，Google AI Studio 要年滿 18 歲才能使用；未滿 18 歲的學員請改用 Gemini 練習（個人帳號年滿 13 歲即可使用）。

什麼是 System Prompt？

每次和 AI 對話時，除了你輸入的問題，背後通常還有一段你看不到的「系統提示詞」，先告訴模型：你是誰、要遵守什麼規則、用什麼格式回答。 它就像員工的工作說明書，整段對話都有效；你的提問則像主管當天交辦的任務。 幾乎所有 AI 產品都靠 System Prompt 決定個性與能力，下一階段的 OpenCode 自訂 Agent，本質上也是「一段 System Prompt＋可用的工具」。

API 是什麼：從聊天視窗走進自己的程式

在 Gemini 網頁上聊天，是「你」跟 AI 對話；API（應用程式介面）則是讓「你的程式」直接跟 AI 對話。學會 API，就能把 AI 放進自己做的網頁、表單、小工具裡。 一次 API 呼叫只有三個元素：① 網址（要找哪個服務）② API Key（證明你是誰，像通行證）③ 用 JSON 格式寫的請求內容（用哪個模型、要問什麼）。AI 回傳的結果同樣是 JSON，程式再從裡面取出文字。 本課使用 gemini-3.5-flash-lite：Gemini 3.5 系列中速度最快、成本最低的模型，Gemini API 免費方案即可使用，很適合練習與做小工具。 本課範例採用 Google 建議新專案使用的 Interactions API（網址結尾為 /interactions）。網路上很多舊教學使用 generateContent，也還能用，但寫法不同，看到時不要混在一起。

金鑰安全：不能放前端，也不能放上網

API Key 就像你的密碼加上信用卡：別人拿到就能用你的額度、以你的名義呼叫 AI；如果你的專案開了帳單，費用也會算在你頭上。 規則一：不要把金鑰寫進前端程式碼（HTML、JavaScript）。網頁送到瀏覽器後，任何人按 F12 或「檢視原始碼」都看得到，混淆或藏在別的檔案裡也沒用。 規則二：不要把金鑰放上網路。包含 GitHub（公開或私人倉庫都不要）、雲端硬碟共用資料夾、部落格文章、截圖與教學影片。網路上有程式專門在掃描外洩的金鑰。 規則三：自己想辦法保管好。可以存在密碼管理器，或放在專案的 .env 檔，並把 .env 加進 .gitignore，確保它不會被上傳。 規則四：要給別人用的網站，金鑰一定要嵌在後端伺服器（環境變數）裡，由前端呼叫你自己的後端，後端再代為呼叫 Gemini（下一站鍊金工房會帶你做）。 萬一外洩：立刻到 AI Studio 的 API Keys 頁面刪除那把金鑰，再建立新的一把。

const API_URL = "https://generativelanguage.googleapis.com/v1beta/interactions";
const MODEL = "gemini-3.5-flash-lite";

// 送出請求，回傳 { id, text }
async function askGemini(apiKey, body) {
  const res = await fetch(API_URL, {
    method: "POST",
    headers: { "Content-Type": "application/json", "x-goog-api-key": apiKey },
    body: JSON.stringify({ model: MODEL, ...body })
  });
  const data = await res.json();
  if (!res.ok) {
    // 錯誤訊息有時直接回傳，有時包在陣列裡，兩種都處理
    const error = [].concat(data)[0]?.error;
    throw new Error(error?.message || "HTTP " + res.status);
  }
  // 只取最後一次提問之後、模型輸出的文字
  const steps = data.steps || [];
  const start = steps.findLastIndex(s => s.type === "user_input") + 1;
  const text = steps.slice(start)
    .filter(s => s.type === "model_output")
    .flatMap(s => s.content || [])
    .filter(c => c.type === "text")
    .map(c => c.text)
    .join("");
  return { id: data.id, text: text || JSON.stringify(data, null, 2) };
}

  const out = document.querySelector("#answer");
  const apiKey = document.querySelector("#key").value.trim();
  if (!apiKey) { out.textContent = "請先貼上 API Key"; return; }
  out.textContent = "思考中…";
  try {
    const result = await askGemini(apiKey, {
      input: document.querySelector("#question").value
    });
    out.textContent = result.text;
  } catch (err) {
    out.textContent = "發生錯誤：" + err.message;
  }
};
</script>

範例三：多輪對話與錯誤處理

API 預設每次呼叫都是全新的對話。Interactions API 會回傳一個 id，下一次呼叫時把它放進 previous_interaction_id，AI 就會接著上一輪的內容回答，不必自己重送整段歷史。 常見錯誤：400 加上 API_KEY_INVALID 表示金鑰貼錯或已被刪除；429 表示超過免費額度，請稍等或隔天再試；網路錯誤則先檢查網址與連線。把錯誤訊息顯示在畫面上，除錯會容易很多。

範例四：結構化輸出，讓 AI 回固定格式的 JSON

AI 平常回的是一段文字，程式很難從裡面準確取出「題目是什麼、答案是哪個」。加上 response_format，把 mime_type 設成 application/json，再用 schema（JSON Schema）描述有哪些欄位，AI 就會照這個格式回答。程式用 JSON.parse 轉成物件後，就能直接做成測驗、表格或存起來。 schema 要寫清楚欄位名稱、型別（string 文字、integer 整數、array 陣列、object 物件）和必填欄位（required）；欄位加上 description 說明用途，AI 會填得更準。 注意：有些限制（例如字數上下限）不一定會被強制遵守，程式拿到資料後仍要自己檢查一次再使用。

正式上線：把金鑰嵌在後端

// ① 同資料夾建立 .env，內容只有一行（不要上傳這個檔案）：
//    GEMINI_API_KEY=貼上你的金鑰
// ② 建立 .gitignore，寫入一行：.env
// ③ 把星門渡口的範例一存成同資料夾的 index.html，刪掉金鑰欄位，
//    並把 askGemini 裡的 fetch 改成呼叫自己的後端（不帶金鑰）：
//    fetch("/api/ask", { method: "POST",
//      headers: { "Content-Type": "application/json" },
//      body: JSON.stringify({ input: "你的問題" }) })
// ④ 啟動（Node.js 22 以上）：node --env-file=.env server.mjs
//    再用瀏覽器開啟 http://localhost:3000

import http from "node:http";
import { readFile } from "node:fs/promises";

const API_URL = "https://generativelanguage.googleapis.com/v1beta/interactions";

http.createServer(async (req, res) => {
  try {
    // 提供前端網頁
    if (req.method === "GET" && req.url === "/") {
      res.writeHead(200, { "Content-Type": "text/html; charset=utf-8" });
      res.end(await readFile("index.html"));
      return;
    }
    if (req.method !== "POST" || req.url !== "/api/ask") {
      res.writeHead(404).end();
      return;
    }
    let raw = "";
    for await (const chunk of req) raw += chunk;
    const { input } = JSON.parse(raw || "{}");
    if (typeof input !== "string" || !input || input.length > 2000) {
      res.writeHead(400, { "Content-Type": "text/plain; charset=utf-8" });
      res.end("問題不可空白，且不超過 2000 字");
      return;
    }
    // 由後端代為呼叫 Gemini，金鑰只在伺服器上
    const upstream = await fetch(API_URL, {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "x-goog-api-key": process.env.GEMINI_API_KEY
      },
      body: JSON.stringify({ model: "gemini-3.5-flash-lite", input })
    });
    res.writeHead(upstream.status, { "Content-Type": "application/json; charset=utf-8" });
    res.end(await upstream.text());
  } catch (err) {
    res.writeHead(500, { "Content-Type": "text/plain; charset=utf-8" });
    res.end("伺服器發生錯誤：" + err.message);
  }
}).listen(3000, () => console.log("已啟動：http://localhost:3000"));

Agent 是什麼？主要 Agent 與子 Agent

在 OpenCode 裡，一個 Agent＝一段 System Prompt＋偏好的模型＋權限規則＋名稱與說明，就像一位有固定職責的助手。 主要 Agent（primary）是直接跟你對話的那位，例如 Build 與 Plan；終端機版用 Shift+Tab 或 /agents 切換。 子 Agent（subagent）由主要 Agent 派出去做事，例如 Explore 去搜尋資料。子 Agent 在乾淨的新對話中工作，做完把結果交回來，不會塞滿主對話。 你只要用白話說「請用 reviewer 子 Agent 檢查我的修改」，主要 Agent 就會派它出動。

用一個 Markdown 檔建立自訂 Agent

在專案建立 .opencode/agents/ 資料夾，新增 reviewer.md，檔名就是 Agent 的名稱；想讓所有專案都能用，就放在 ~/.config/opencode/agents/。 檔案開頭用 --- 包住的設定區（frontmatter）常用欄位： description：這個 Agent 做什麼。子 Agent 一定要寫，主要 Agent 靠它決定要派誰。 mode：primary、subagent 或 all（兩者皆可），沒寫時預設為 primary。 model：指定模型，格式為「供應商/模型」，例如 opencode/big-pickle；沒寫時沿用目前對話的模型。 steps：最多執行幾步，避免 AI 停不下來。 設定區下面的內文，就是這個 Agent 的 System Prompt。

權限：讓 Agent 只做該做的事

permissions 是一串規則，每條有三個欄位：action（動作，如 edit 修改檔案、shell 執行指令、read 讀檔、webfetch 讀網頁）、resource（對象，可用 * 代表全部）、effect（allow 允許、ask 每次詢問、deny 禁止）。 重要觀念：符合的規則中「最後一條」生效，所以先寫大範圍規則，再寫例外。 例如審稿 Agent 只需要讀，就把 edit 與 shell 設為 deny，它就算想改檔案也做不到。 注意：網路上 OpenCode 1 的舊教學使用 tools、permission、prompt 等欄位，2 代新設定請改用本島的寫法。

Skill：需要時才打開的技能包

Skill 是一個資料夾，裡面最重要的是 SKILL.md，寫著「某一類任務該怎麼做」，旁邊還能放範本、參考資料與腳本。 它跟 AGENTS.md 最大的差別：AGENTS.md 每次都會載入；Skill 平時只讓 AI 看到名稱和描述，遇到相關任務才把完整內容載入，不會白白占用 AI 的注意力（上下文）。 在 Gemini 裡 Skills 需要付費方案，在 OpenCode 則免費就能使用。

L13 高階｜Agent＝模型＋Harness：設計讓 AI 穩定做對事的整套系統

學習目標：能說明 Harness 的組成，拆解 OpenCode 如何組合提示詞、工具與權限，並用前幾課的功能組出一套有檢查機制的工作流程。

Agent＝模型＋Harness

Harness 原意是馬具：模型是馬，力量很大；Harness 是韁繩、馬鞍與路線，決定這股力量能不能用在對的地方。 在 AI Agent 裡，Harness 指模型以外的一切：System Prompt、專案規則、可用工具、權限、上下文管理、子 Agent，以及檢查結果的回饋機制。 同一個模型放在不同的 Harness 裡，表現可能差很多。這也是 2026 年 AI 圈最常討論的主題：從「怎麼問」（提示詞工程）、「給它看什麼」（上下文工程），進化到「設計整套環境」（Harness 工程）。

拆解 OpenCode 的 Harness

依官方文件，OpenCode 每次送給模型的指示依序組合：① Agent（或模型供應商）的 System Prompt → ② 程式模式的工具說明（有啟用時）→ ③ MCP、參考資料與 Skill 的說明 → ④ 全域與專案的 AGENTS.md，以及設定中的 instructions → ⑤ 日期與環境資訊。這些是「合併」而不是互相覆蓋。 接著進入 Agent 迴圈：模型決定要用哪個工具 → OpenCode 先檢查權限（allow／ask／deny）→ 執行並把結果交回模型 → 模型決定下一步，直到完成或達到 steps 上限。 對話快塞滿模型的上下文時，OpenCode 會自動壓縮（compaction）：把較早的對話整理成摘要，並保留最近一段原文，讓工作能繼續。子 Agent 則在全新的上下文中工作，避免主對話被細節淹沒。 你在前幾座島學到的 AGENTS.md、Skill、MCP、自訂 Agent 與權限，全都是在調整這套 Harness。

兩種控制：事前引導與事後檢查

好的 Harness 同時有兩種控制： 事前引導（feedforward）：在 AI 動手前告訴它怎麼做，例如 System Prompt、AGENTS.md、Skill、範本。 事後檢查（feedback）：在 AI 做完後驗證結果，例如執行測試或檢查指令、讓只讀的 reviewer 子 Agent 審查、列出修改清單給人確認。 只有引導沒有檢查，錯誤會悄悄溜過；只有檢查沒有引導，AI 會一直重複犯同樣的錯。 核心習慣：AI 每犯一次錯，不只是叫它改，而是問「要加哪一條規則或哪一個檢查，下次就不會再發生？」然後把它寫進 Harness。

實作：組出你的迷你 Harness

把前幾課的元件組合起來： 1. AGENTS.md 寫清楚「完成標準」與「完成前檢查」（事前引導）。 2. 建立只讀的 reviewer 子 Agent，用權限禁止它修改檔案（事後檢查）。 3. 建立 /ship 自訂指令，固定「計畫 → 執行 → 審查 → 修正 → 回報」的流程。 4. 在 opencode.jsonc 設定全域權限：執行指令前先詢問、禁止推送到遠端、存取專案外的資料夾要詢問（安全護欄）。 先用免費模型跑一次，觀察哪裡出錯，再回頭調整規則或檢查。這個「觀察 → 調整 Harness → 再試」的循環，就是 Harness 工程的日常。
